# Build Note — EV Tipping Point Finder Prototype

---

## 1. What Was Built

A four-panel static web tool (single HTML file + inline CSS/JS) deployable to GitHub Pages. No backend, no build step. The tool walks a user through: country selection → live BEV share display → commute cost inputs → personalised savings output. All arithmetic runs in the browser. The only external call is a live Eurostat API fetch that runs on page load.

---

## 2. The Live Data Query Used

**Endpoint:** Eurostat JSON-stat REST API
`https://ec.europa.eu/eurostat/api/dissemination/statistics/1.0/data/road_eqr_carmot`

**Parameters (appended as query string):**

- `format=JSON`
- `lang=EN`
- `mot=BEV` — filters to battery electric vehicles only
- `unit=NR` — returns absolute registration counts (number of vehicles)
- `time=2023` — pins the request to the 2023 reference year
- `geo=PL&geo=RO&geo=HU&geo=ES&geo=PT&geo=CZ&geo=SK&geo=GR` — the eight target markets

The fetch also pulls the same endpoint a second time with `mot=TOT` (total new passenger car registrations) for the same geos and year. Both calls are fired in parallel via `Promise.all()` on page load. BEV share per country is computed in the browser by dividing BEV count by TOT count. No share percentages are hardcoded.

If either fetch fails or returns a null cell for a given country, the tool displays a labelled fallback banner ("Live data unavailable — showing last verified figures") and falls back to a small static object defined in the JS. The fallback is explicit to the user; it is never silent.

---

## 3. What's on Screen and How It Updates

**On page load (before any user action):**
- The fetch fires immediately.
- A loading spinner occupies the country card area.
- Once both API responses resolve, the spinner is replaced by a horizontal adoption spectrum bar rendered in SVG. The bar runs from 0% to 85% (Norway reference point, labelled). The EU mean marker (computed from the fetched data, not hardcoded) is pinned on the bar. No country dot is placed yet — the bar is in its neutral, unselected state.
- The country dropdown is populated from the same fetched data (only countries with non-null BEV and TOT values appear as options).

**On country selection (user action — dropdown change):**
- The selected country's dot animates onto the spectrum bar at its computed BEV share position.
- The share figure and absolute BEV registration count update in the callout text below the bar. The "X people made the switch last year" counter (Screen 4) also pulls from this fetched absolute BEV count — it is the same number, displayed in two places.
- The non-EV share inverse ("~X% of new cars in your country were not electric last year") is computed live from the fetched share.

**On commute form submission (user action — button click):**
- Screens 2 and 3 are in the DOM from initial load but hidden. The submit button on Screen 2 unhides Screen 3.
- Monthly savings, break-even month, and the 36-month timeline bar all compute from: user-entered km, user-entered fuel spend, and two editable constants at the top of the JS block (electricity cost per 100km, CityVolt monthly lease placeholder). These constants are clearly labelled as configurable and are not fetched — they are CityVolt-specific business inputs.
- The break-even bar re-renders immediately on input change (live, no submit required after the first submission).

**Screen 4 (CTA):**
- Visible after Screen 3 renders.
- The "X people switched" counter reads from the already-fetched BEV absolute registration value for the selected country. No second fetch.
- Email + city capture writes to a `mailto:` link for prototype purposes (no form backend).

---

## 4. What Was Cut and Why

**Cut: the multi-screen stepped flow (Screens 1 → 2 → 3 → 4 as separate pages/views).**

Iris's concept describes four distinct screens navigated sequentially. In the prototype this becomes a single scrollable page with four anchored sections, with progressive disclosure (sections 2–4 hidden until their trigger conditions are met). Reason: a true multi-screen SPA router adds JavaScript complexity (state management, history API, back-button handling) that is out of scope for a first shippable prototype and introduces failure points with no corresponding increase in data fidelity. The core interaction — live data fetch, computed share placement, personalised savings — is fully preserved. The scroll-based layout can be converted to a routed flow in a subsequent build iteration once the data pipeline is confirmed working in production.
